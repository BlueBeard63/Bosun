# Registering packages without blank imports

Bosun controllers, services and middleware register themselves with package-level declarations such as `var _ = bosun.Controller[UsersController]("/users")`. Those declarations only run when their package is imported. As an app grows, `main.go` collects a list of blank imports that exist only to trigger them:

```go
import (
    _ "example.com/shop/internal/auth"
    _ "example.com/shop/internal/billing"
    _ "example.com/shop/internal/health"
    _ "example.com/shop/internal/users"
    // ...one more for every new package, easy to forget
)
```

This page explains why Go needs those imports, and shows the two supported ways to keep them out of `main.go`: a generated registry file (recommended), or a hand-written aggregator package.

## Why the imports are needed

Go initialises a package, which runs its `var` declarations and `init` functions, only if the package is part of the program, and a package is only part of the program if something imports it. A package nothing imports isn't compiled into the binary at all, so no runtime mechanism can find its controllers. Reflection only sees types that are linked in, and scanning the filesystem at runtime would find source files the binary doesn't contain.

So discovery has to happen when you build, not when the app runs. Bosun does it the way the Go toolchain expects: it generates ordinary Go code that imports the packages, and the compiler checks those imports like any others. Builds stay reproducible, and a missing or misspelled package is a compile error, not a route that silently never appears.

## Option 1: generate the imports (recommended)

`bosun gen registry` scans your module for packages that register with Bosun and writes `zz_bosun_registry.go`, a file of blank imports, into the package that calls `bosun.New()`.

### Set it up

Add a `go:generate` directive to `main.go` and remove the hand-written side-effect imports:

```go
package main

//go:generate bosun gen registry

import (
    "log"

    "github.com/bluebeard63/bosun"
)

func main() {
    if err := bosun.New().Run(":8080"); err != nil {
        log.Fatal(err)
    }
}
```

Generate the file:

```sh
go generate ./...
```

```go
// Code generated by bosun gen registry. DO NOT EDIT.

package main

import (
    _ "example.com/shop/internal/billing" // Service[memStore], DefaultBind[Store, memStore], Middleware[Auth]
    _ "example.com/shop/internal/users"   // Service[Repo], Controller[UsersController]
)
```

Commit the generated file like any other source. Each import is annotated with what the package registers, so a code review shows exactly what a new package adds to the app. Services created with `bosun new service` are already set up this way.

### Keep it current

Run `go generate ./...` after adding, removing or moving a package that registers with Bosun. To catch a forgotten regeneration, check the file in CI:

```sh
bosun gen registry --check
```

`--check` writes nothing and exits non-zero when the file doesn't match what would be generated:

```
Error: zz_bosun_registry.go is out of date; run bosun gen registry (or go generate)
```

### What gets imported

The generator parses the module's source with the Go standard library (no build and no reflection) and includes a package when one of its non-test files has a package-level declaration calling `bosun.Controller`, `Service`, `Middleware`, `Default`, `DefaultBind` or `DefaultDynamic`. Any import name for the bosun package is recognised, for example `b "github.com/bluebeard63/bosun"`.

It skips:

- `_test.go` files;
- `vendor`, `testdata`, and directories whose names start with `.` or `_`;
- nested modules (directories with their own `go.mod`);
- the target package itself;
- other `package main` directories, which Go can't import. The generator prints a note for each one.

The output is sorted by import path, so it is the same on every machine.

### Where to put the file

Generate the file into the package that calls `bosun.New()`. Go only allows importing a package under `internal/` from inside the directory tree rooted at that `internal/` directory's parent. A file at the module root or in `cmd/<name>` can import everything under the module's `internal/`. A file elsewhere can be refused, and in that case the generator stops with an error naming the packages, instead of writing a file that won't compile.

For a module with several binaries, give each binary's `main` package its own directive and file. Use `--dir` to write into another package and `--out` to change the file name:

```sh
bosun gen registry --dir ./cmd/worker
```

| Flag | Default | Description |
| --- | --- | --- |
| `--dir` | `.` | Package directory to write into: the one that calls `bosun.New()`. |
| `--out`, `-o` | `zz_bosun_registry.go` | File name, relative to `--dir` (or an absolute path). |
| `--check` | `false` | Verify the file is up to date instead of writing it. |

### Limitations

- **Only package-level `var` declarations are detected.** A registration made inside `init()` or another function isn't found. Use the `var _ = bosun.X[...]()` form, which is the Bosun convention anyway, or import that package by hand.
- **Build tags are ignored.** The generator reads every non-test file whatever its `//go:build` line. If a package is excluded entirely under some tags, import it by hand from a file with the same tags rather than relying on the generated file.
- **Every registering package is imported.** That is the point, but it also means a package you deliberately keep out of one binary needs its own target, or `bosun.Disable(pkgPath)` at runtime.

## Option 2: an aggregator package

If you'd rather not generate code, collect the imports in one small package and import that once from `main.go`:

```go
// internal/app/app.go
// Package app wires every package that registers with Bosun.
package app

import (
    _ "example.com/shop/internal/billing"
    _ "example.com/shop/internal/users"
)
```

```go
// main.go
import _ "example.com/shop/internal/app"
```

`main.go` stays short, and the list lives next to the code it describes. You still maintain the list by hand. You can also combine the two options: put `//go:generate bosun gen registry` in `internal/app/app.go`, and the generated file will live there.

## Recommended project structure

```text
shop/
├── go.mod
├── main.go                  // bosun.New().Run(...), //go:generate bosun gen registry
├── zz_bosun_registry.go     // generated: blank imports
└── internal/
    ├── users/               // var _ = bosun.Controller[UsersController]("/users")
    ├── billing/             // var _ = bosun.Service[...], bosun.Middleware[...]
    └── dto/                 // plain types only: not imported by the registry
```

Keep shared types that should never register anything (DTOs, event payloads, generated clients) in packages without registrations. The [microservices guide](./microservices.md) calls this the contracts package. Importing such a package for its types never pulls another service's controllers into your binary.
